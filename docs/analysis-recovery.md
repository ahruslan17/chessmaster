# Анализ: состояния и ручное восстановление

Engine-анализ и объяснения — разные задания. Открытие партии, GET анализа и SSE
читают только сохранённое; LLM не вызывается из чтения. Объяснения запускаются
отдельной кнопкой для явно выбранного цвета. Поворот доски цвет ученика не меняет.

## Перед проверкой

- Используйте отдельные PostgreSQL/Redis/worker; не выполняйте команды на production
  без разрешения. Не публикуйте DB/Redis во внешнюю сеть.
- API и worker должны использовать одну версию приложения и совместимую схему БД.
- Сначала применяются additive-миграции (`alembic upgrade head`) в разрешённой БД.
  Старые результаты не становятся исправленными от одной миграции: для typed
  cp/mate требуется явный повтор engine-анализа.
- Пустые `LLM_API_KEY` и `LITELLM_BASE_URL` отключают coach. Настроенный провайдер
  сам по себе не является разрешением расходовать бюджет.

## Наблюдение

```bash
curl "$BASE/api/games/$GAME_ID/analysis/status?player_color=white"
curl "$BASE/api/games/$GAME_ID/analysis?player_color=white"
```

`BASE` — адрес вашего разрешённого стенда. `engine_status`: `pending`, `queued`,
`in_progress`, `done`, `failed`. Сохранены UUID попытки, Celery task ID, heartbeat,
счётчик обработанных позиций и ошибка. Состояние coach относится к выбранной стороне.
`done` движка не означает готовность учебных объяснений. Частичный текст сохраняется
при ошибке объяснений; валидная структура не доказывает шахматную истинность текста.

Длительность сама по себе не доказывает зависание. Проверьте процессы worker,
доступность Redis/DB, логи и продвижение счётчика. Отсутствие heartbeat — повод
диагностировать, а не автоматически объявлять неуспех длинной партии.

## Обычный повтор после ошибки

```bash
curl -X POST "$BASE/api/games/$GAME_ID/analysis/start" \
  -H 'Content-Type: application/json' -d '{}'
curl -X POST "$BASE/api/games/$GAME_ID/analysis/explanations" \
  -H 'Content-Type: application/json' -d '{"player_color":"white"}'
```

Первая команда запускает/повторяет engine только когда это нужно; дубль активного
задания не сбрасывает данные. Вторая переиспользует готовый совместимый engine-результат
и не запускает Stockfish. Для чёрных передайте `black`. Без настроенного coach
возвращается понятная ошибка; engine-данные остаются.

## После подтверждённой остановки worker или потери публикации

Задание сначала сохраняется в БД, затем публикуется. При подтверждённой ошибке брокера
именно queued-попытка помечается failed. Краш API между commit и публикацией может
оставить queued без сообщения. Автономный outbox/reaper в MVP не вводится: нужен
явный recover после диагностики.

1. Устраните причину остановки/недоступности зависимостей в разрешённой среде.
2. Прочитайте status и скопируйте UUID **наблюдённой** попытки.
3. Подтвердите восстановление в UI либо отправьте запрос ниже.

```bash
curl -X POST "$BASE/api/games/$GAME_ID/analysis/start" \
  -H 'Content-Type: application/json' \
  -d '{"recover":true,"expected_attempt_id":"UUID_FROM_STATUS"}'
curl -X POST "$BASE/api/games/$GAME_ID/analysis/explanations" \
  -H 'Content-Type: application/json' \
  -d '{"player_color":"white","recover":true,"expected_attempt_id":"UUID_FROM_REVIEW"}'
```

Если попытка уже изменилась, `409`: перечитайте состояние, не повторяйте старый recover
вслепую. Для legacy-задания без UUID явно передаётся `null`. Новый UUID лишает старую
попытку права менять текущие данные; поздний результат/ошибка игнорируются. Это
защита записи, не обещание немедленной остановки старого CPU-процесса.

## Совместимость и ограничения

- Существующие URL чтения и ключи ответа сохраняются. Новые поля additive.
- GET commentary stream отдаёт только сохранённый текст, без него — `404` с указанием
  явного запуска. Восстановление старой автогенерации на GET запрещено.
- Accuracy остаётся nullable deprecated API-полем, но не показывается и не используется
  в prompts/советах. Старые непроверенные тексты не выдаются за исправленные.
- Engine-result имеет отдельный UUID. Объяснение привязано к стороне и этому результату;
  текст от прежнего расчёта не подмешивается в новый.
- Синтетические/mocked проверки надёжности не заменяют реальные разрешённые LLM-разборы
  и экспертную оценку M07–M09.
