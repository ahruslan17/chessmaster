# Локальное подключение LLM

Текущая локальная конфигурация использует OpenAI-compatible endpoint LiteLLM из
OpenCode. Глобальный конфиг OpenCode не меняется и не читается приложением на каждом
запуске. Значения перенесены в ignored `.env`; ключ нельзя добавлять в документацию,
коммиты или вывод диагностических команд. Права локального `.env`: `0600`.

```dotenv
LLM_MODEL=openai/gpt-6.1-sol
LLM_ALTERNATIVE_MODEL=openai/gpt-5.6-terra
LITELLM_BASE_URL=https://litellm.gearwap.ru/v1
# LLM_API_KEY задаётся локально, без публикации значения
```

Префикс `openai/` выбирает в Python LiteLLM совместимый транспорт. Провайдер получает
собственное имя модели без префикса. Версии подтверждены каталогом OpenCode и
read-only `/v1/models` провайдера на 2026-10-16.

`LLM_MODEL` — модель приложения. `LLM_ALTERNATIVE_MODEL` — сохранённый вариант для
явного сравнения; сейчас автоматического fallback, второго вызова и выбора модели
в UI нет. Чтобы использовать Terra в отдельном запуске, явно выберите её через
параметр сервиса либо `LLM_MODEL` окружения этого запуска. Не переключайте общую
модель действующего worker посреди задач.

Настройка подключения сама по себе не разрешает неограниченные расходы. Для M06
согласован общий лимит $10 на два synthetic-разбора и адресные повторы. Проверочный
harness резервирует стоимость перед каждым HTTP-запросом, ограничивает выходные
токены и число запросов, отключает автоматические повторы. Это ограничение тестового
прогона, не глобальная финансовая квота приложения. Для постоянного использования
нужен отдельный budget-limited ключ или серверный лимит провайдера.

Просмотр партий не вызывает модель. Новый импорт автоматически запускает только
engine; полный походовый разбор запускается кнопкой «Комментировать все ходы»
или POST `/api/games/{game_id}/analysis/explanations` с выбранным `player_color`.

## Полный походовый разбор

По требованию от 2026-10-26 комментарий нужен каждому полуходу обеих сторон:
теоретическому, лучшему, хорошему и ошибочному. Ограничение прежнего M06 только
выбранными ошибками больше не применяется к комментариям. Подборка учебных моментов
сохраняется отдельно и зависит от выбранной стороны.

Worker отправляет не больше пяти недостающих полуходов в одном запросе. В контексте
есть реальные позиции, оценки и легальные линии Stockfish; гипотетические ветки
отделены от фактического хода. Структурная проверка не гарантирует шахматную
правильность текста: комментарии требуют экспертной оценки.

Каждый полученный пакет сохраняется сразу. Новые полные разборы используют
структурированные комментарии версии 2; статус `done` требует валидного комментария
этой версии для каждого полухода. При пропусках или сбое сохраняется частичный результат.
Кнопка «Дополнить комментарии» обрабатывает недостающие ходы, не повторяет Stockfish
и не перезаписывает готовые комментарии версии 2. Автоматических платных повторов нет.
Тайм-аут одного пакета — 180 секунд, предел ответа — 8192 токена.
Полный разбор не задаёт `temperature`: текущая reasoning-модель отклоняет
`temperature: 0.4` с HTTP 400. Используется значение провайдера по умолчанию;
автоматического повторного запроса с другими параметрами нет.

Полный разбор общий для обеих сторон: смена стороны не создаёт второй набор текстов
и не вызывает модель. Существующее хранилище `SideReview` сохраняет владельца попытки,
а `context.commentary_scope = "all_moves"` обозначает общий разбор. API показывает
сохранённые комментарии обеих сторон и учебные моменты выбранной стороны. Старые
разборы не становятся полными автоматически: их расширяет явный запуск.

## Формат комментария и обновление старого разбора

`SideReview.comments[move_index]` хранит объект с `version: 2`, блоком `played`
и необязательными `alternative` и `comparison`. В блоках объяснения обязательно
только `idea`; `pros`, `cons`, `tactics`, `plan`, `opponent_reply` и
`missed_opportunity` могут отсутствовать или быть `null`. Старые строки остаются
доступны как `{ "text": "..." }`; миграция JSONB не требуется.

Обычный POST объяснений не обновляет завершённый полный разбор со старым текстом.
При расширении прежнего разбора выбранных моментов до всех полуходов обычный
запрос заполняет только отсутствующие комментарии. Прежние объяснения, итог
и рекомендации сохраняются; новые комментарии могут иметь версию 2, но это
не включает обновление уже готовых записей.
Обычная кнопка «Разобрать партию» сразу запрашивает формат с обоими объяснениями;
отдельного пользовательского режима «подробный разбор» нет. Для совместимости API
старый запрос без `detailed` остаётся идемпотентным; интерфейс отправляет:

```json
{ "player_color": "white", "detailed": true }
```

Такой запрос задаёт `context.commentary_version = 2`. Worker считает старые
и структурно некорректные записи недостающими, но сохраняет их видимыми, пока
не получит новые объяснения. Каждый готовый пакет заменяет только соответствующие
старые записи; уже валидные комментарии версии 2 остаются прежними. Незавершённое
обновление требует явного продолжения. Повторный запрос во время активной попытки
не создаёт другую попытку; выбранный цвет не меняет владельца общего разбора.
Обновление не запускает движок и сохраняет прежний `engine_result_id`.
