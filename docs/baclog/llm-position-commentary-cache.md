# BL-001. Общий кэш LLM-комментариев к позициям и ходам

Дата: 2026-10-26.

Статус: **отложено по решению Руслана**. Сейчас не реализовывать и не включать в первый объём улучшения разбора. Вернуться после отдельного согласования.

## Задача

Снизить расходы на повторную генерацию: если позиция и конкретный ход уже встречались, использовать пригодный сохранённый комментарий вместо нового LLM-запроса.

Основной риск — распространить неверный совет между партиями. Простое сохранение всех ответов LLM в общий словарь не подходит.

## Текущее поведение

На момент исследования (`ad0398c`) комментарии сохраняются в `SideReview` внутри конкретного разбора. Готовый полный разбор переиспользуется, повтор обрабатывает пропуски. Общего межпартийного кэша «позиция + ход» нет.

Владельцы поведения:

- `src/app/models/side_review.py` — сохранённый разбор;
- `src/app/services/game_review.py` — запуск и переиспользование разбора;
- `src/app/tasks/analysis.py` — пакетная генерация и сохранение;
- `src/app/services/llm_coach.py` — запросы к LLM и валидация.

## Предлагаемые границы

| Тип объяснения | Общий кэш |
|---|---|
| Самостоятельная идея хода, изменения позиции, подтверждённые последствия | Допускается при совпадении условий и одобрении записи |
| Стратегический план, следующий из самой позиции | Возможен после проверки; нельзя переносить неподтверждённую интерпретацию как факт |
| Связь с предыдущими событиями партии, личными ошибками или прогрессом ученика | Не переиспользовать по одному ключу позиции и хода |
| Итог партии, личные рекомендации и заметки | Не включать в общий позиционный кэш |

Текущая генерация пакетами по пять полуходов не гарантирует самостоятельность текста. Перед общим использованием комментарий должен обходиться без ссылок на соседние комментарии, чужую историю и личные данные.

## Идентичность запроса

Предлагается хэш канонического набора полей, с сохранением самих полей для проверки совпадения:

- вариант шахмат, расположение фигур, очередь хода, права рокировки и возможность взятия на проходе;
- счётчик правила 50 ходов и история повторений, когда они влияют на вывод;
- конкретный легальный ход в UCI;
- язык, уровень объяснения и перспектива комментария;
- версия контракта генерации, промпта и проверок;
- данные или условия совместимости анализа движка.

Сторона хода уже входит в состояние позиции. Она отличается от стороны, выбранной для учебной подборки: её переключение не должно дробить общий кэш самостоятельных объяснений.

Номер полного хода можно исключить только из текста, который от него не зависит. Одинаковое расположение фигур недостаточно для совпадения запроса. Политика канонизации и совместимости требует отдельного проектирования и тестов.

## Защита от плохих советов

| Состояние записи | Значение | Повторная выдача в других партиях |
|---|---|---|
| `candidate` | Сохранённый ответ, ещё не допущенный к общему использованию | Нет |
| `approved` | Прошёл согласованную проверку качества | Да, при совместимых условиях |
| `quarantined` | Есть жалоба или обнаружено противоречие | Нет |
| `rejected` | Ошибка подтверждена | Нет |

Принципы допуска:

1. Проверять поддерживаемые утверждения по структурированным фактам доски и анализа: фигуры, поля, материал, линии и последствия. Валидный JSON и легальная линия не доказывают правильность всего текста.
2. Для первой версии допускать свободные объяснения в общий кэш после проверки тренером; начать с часто встречающихся позиций. Существующие тексты не одобрять массово.
3. Вторую LLM можно использовать для поиска подозрительных мест, но её согласие не заменяет фактическую или экспертную проверку.
4. Жалоба может инициировать карантин или проверку по согласованной политике. Пользователь не должен иметь возможности подменить общий текст своим.
5. Хранить происхождение, редакцию и основание одобрения. Отзыв должен прекращать будущую выдачу и помечать либо скрывать отозванный текст при чтении уже сохранённых разборов. Одной блокировки исходной записи при независимых копиях текста недостаточно.

## Предлагаемая реализация после согласования

- Отдельная таблица в существующем PostgreSQL с уникальным индексом по ключу. Новая векторная база и RAG не нужны.
- Сначала поиск одобренной совместимой записи, затем генерация только промахов. Новые ответы сохраняются кандидатами и в исходном разборе согласно его контракту.
- Координация одновременных запросов одного ключа: ограниченное ожидание, восстановление после сбоя владельца и отсутствие бессрочной блокировки. Ожидание кандидата не разрешает выдавать его как одобренный ответ.
- Проверка кэша до требования доступности LLM: одобренное попадание должно работать и при отключённой генерации.
- Версионирование и проверка совместимости: обновлённый движок или промпт не должны приводить к скрытой платной перегенерации.
- Метрики попаданий, промахов, карантина, времени и фактического расхода. Не проверять каждый кэш-хит дополнительным платным запросом.
- Общий текст не содержит имён, личных заметок, идентификаторов сессий или других данных владельца партии. Ссылки на частный исходный разбор недоступны другим пользователям.

Python-словарь не подходит как постоянное общее хранилище нескольких worker. Redis можно оценить позже, только если измерения покажут необходимость ускорения чтения.

## Критерии приёмки

| Проверка | Ожидаемый результат |
|---|---|
| Одна позиция, тот же ход, совместимые условия, запись `approved` | Новый LLM-запрос не выполняется |
| Другой ход, сторона хода, права рокировки или значимый контекст ничьей | Неподходящий комментарий не переиспользуется |
| Переключение стороны учебной подборки или повторное открытие партии | Нет дополнительных запросов генерации |
| Несовместимые классификация, альтернатива или вывод движка | Старое объяснение не выдаётся без проверки совместимости |
| Запись `candidate`, `quarantined` или `rejected` | Нет автоматической межпартийной выдачи |
| Отзыв ранее одобренной редакции | Она не появляется в новых выдачах и не показывается как действующая в сохранённых разборах |
| Параллельные задачи и сбой генератора | Координация не допускает обычных дублирующих вызовов; ожидание ограничено; неизвестный расход при аварии не считается нулевым |
| Обновление версии | Старые разборы читаются совместимо; нет скрытого платного обновления |
| Доступ к чужой партии | Через кэш не раскрываются личные данные, исходный разбор и права доступа |
| Известная ошибка `36.Bd3` | Текст о ферзе на `e5`, перекрывающем диагональ `d3–h7`, не получает автоматический допуск |

- Нужны структурированные факты, критерии качества, проверки утверждений и версионирование из [плана улучшения](../features/game-review-improvement-plan.md).
- Согласовать, кто одобряет комментарии, как обрабатывается карантин и как отзываются записи.
- Определить допустимую область повторного использования и условия совместимости движка.
- Решить, какие комментарии остаются доступными только в исходном разборе и как обрабатывается отсутствие одобренного кэш-хита при недоступной LLM.
- Измерить повторяемость позиций и стоимость проверок. Размер экономии пока не установлен.

Бэклог не разрешает миграции БД, изменение текущего анализа, платные проверки, автоматический перенос существующих комментариев или деплой.
